﻿# Multimodal Misinformation Verifier

An evidence-grounded misinformation verification system designed to evaluate claims against supporting or refuting evidence, communicate uncertainty, and provide traceable explanations.

**Project status:** Dataset exploration and audit completed. Evidence retrieval and model development are upcoming.

## Overview

Misinformation verification requires more than classifying a statement as true or false. A reliable system must retrieve relevant evidence, assess whether that evidence supports or refutes a claim, and recognize when the available information is insufficient.

This project aims to develop a modular verification pipeline that prioritizes evidence traceability, measurable performance, uncertainty handling, and reproducibility.

## Objectives

- Retrieve relevant evidence for a given claim.
- Classify claims into `SUPPORTS`, `REFUTES`, or `NOT ENOUGH INFO`.
- Connect predictions to the evidence used to produce them.
- Evaluate retrieval quality and classification performance separately.
- Identify failure cases, uncertainty, and limitations.
- Build toward a multimodal architecture that can incorporate text, images, audio, and video.

These are project objectives, not claims that all features have already been implemented.

## Dataset

The initial dataset exploration uses the FEVER benchmark:

| Split       | Records | Purpose                      |
| ----------- | ------: | ---------------------------- |
| Train       | 145,449 | Training-data exploration    |
| Development |  19,998 | Development-data exploration |

The development split contains 6,666 examples per label in the selected file.

**Labels**

- `SUPPORTS`
- `REFUTES`
- `NOT ENOUGH INFO`

The dataset audit identified duplicate claim texts and some claims associated with conflicting labels. These cases require careful treatment rather than automatic deletion or relabeling.

Raw datasets are kept locally and excluded from Git.

## Planned Architecture

The intended system is organized into modular stages:

1. **Input processing** — accept and validate claims and supported media inputs.
2. **Evidence retrieval** — retrieve relevant source passages or sentences.
3. **Evidence analysis** — assess claim–evidence relationships.
4. **Verification** — predict `SUPPORTS`, `REFUTES`, or `NOT ENOUGH INFO`.
5. **Reliability layer** — report uncertainty and handle insufficient evidence.
6. **Result presentation** — return predictions with traceable evidence and limitations.

The architecture will evolve as individual components are implemented and evaluated.

## Evaluation Strategy

The project will report relevant metrics at each stage:

- **Retrieval:** Recall@k and evidence coverage
- **Classification:** precision, recall, F1-score, macro-F1, and confusion matrix
- **Reliability:** confidence calibration, abstention behavior, and error analysis
- **Engineering:** reproducibility, latency, input validation, and test coverage

Metrics will be reported only after the corresponding component has been implemented and evaluated.

## Engineering Principles

- Evidence-backed predictions instead of unsupported assertions
- Explicit uncertainty when evidence is insufficient
- Separation of retrieval quality from classification quality
- Reproducible data processing and evaluation
- No fabricated performance metrics
- Clear documentation of dataset limitations and model failures
- Modular design for future multimodal support

## Limitations

The current work covers dataset exploration and auditing. A functioning evidence retrieval engine, trained verification model, multimodal processing pipeline, and deployed API are not yet established by this milestone.

FEVER is a benchmark dataset, not a complete representation of real-world misinformation. Benchmark performance alone will not establish factual correctness across arbitrary claims or domains.

﻿# System Architecture

## 1. Document Information

- Project: Multimodal Misinformation Verifier
- Version: 0.1.0
- Status: Proposed architecture
- Target: Text-only MVP

This document describes the intended design. It does not assert that the components have been implemented.

## 2. Architectural Principles

- Evidence before verdict.
- Retrieval relevance is not equivalent to truth.
- Every evidence item must retain provenance.
- Uncertainty and conflicting evidence must be explicit.
- Components should be testable in isolation.
- Dataset and model versions must be traceable.
- The initial design should remain simple enough to evaluate and improve.

## 3. High-Level Data Flow

Claim input
    |
    v
Input validation
    |
    v
Text preprocessing
    |
    v
Evidence retrieval <--- Versioned evidence corpus
    |
    v
Candidate evidence filtering and ranking
    |
    v
Claim-evidence assessment
    |
    v
Verdict policy and uncertainty handling
    |
    v
Result assembly
    |
    v
Structured verification result

The first implementation may use simple lexical retrieval. Semantic embeddings, reranking, and stronger inference models are optional later improvements, not prerequisites for the first baseline.

## 4. Logical Components

### 4.1 Input and validation

Responsibilities:
- Accept a textual claim.
- Validate type, whitespace, and configured length limits.
- Return clear validation errors.
- Avoid interpreting arbitrary user input as executable instructions.

### 4.2 Preprocessing

Responsibilities:
- Apply consistent text normalization.
- Preserve the original claim for display and audit.
- Normalize evidence text without destroying meaningful names, dates, quantities, or negation.
- Record preprocessing configuration.

Normalization must be tested because aggressive transformations can alter claim meaning.

### 4.3 Evidence store

The evidence store shall expose records with a stable schema.

Proposed fields:
- evidence_id: stable unique identifier
- text: evidence passage
- source_title: title when available
- source_url: URL when available and verified
- publisher: publisher name when available
- published_at: publication timestamp when available
- retrieved_at: acquisition timestamp when available
- source_type: documented source category
- dataset_version: version or snapshot identifier

Unavailable metadata must remain missing rather than being invented.

### 4.4 Retrieval

Responsibilities:
- Search the configured evidence corpus.
- Return a bounded list of candidate passages.
- Preserve evidence IDs and source metadata.
- Record retrieval method and parameters.

Initial baseline:
- A simple lexical retrieval method such as TF-IDF or BM25, selected after reviewing the dataset and available dependencies.

Potential future improvements:
- Dense embedding retrieval.
- Hybrid lexical and dense retrieval.
- Cross-encoder reranking.
- Query reformulation.

Retrieval performance must be measured independently from final verdict accuracy.

### 4.5 Claim-evidence assessment

Responsibilities:
- Compare a claim with each candidate evidence passage.
- Determine whether the passage supports, contradicts, or does not resolve the claim.
- Preserve the link between assessment and evidence ID.
- Handle irrelevant and ambiguous passages.

A retrieval score alone shall not determine support or refutation. The first assessment baseline may use documented rules or a selected model, but its limitations must be evaluated.

### 4.6 Verdict policy

The verdict policy combines evidence assessments and applies explicit decision rules.

Possible outputs:
- Supported
- Refuted
- Insufficient evidence
- Review required

The policy must account for:
- Evidence quality and relevance.
- Agreement or disagreement among evidence items.
- Missing or incomplete evidence.
- Contradictory sources.
- Configured decision thresholds, if applicable.

Thresholds must be selected using validation data, not chosen to make reported results look better. The policy should prefer unresolved outcomes when the evidence does not justify a conclusion.

### 4.7 Result assembly

Proposed response fields:
- claim
- verdict
- rationale
- evidence: list of evidence references and assessment details
- warnings
- unresolved_questions
- pipeline_version
- dataset_version

Optional scores may be included only when their meaning is documented. They must not be described as calibrated confidence without appropriate validation.

### 4.8 Evaluation

Responsibilities:
- Evaluate retrieval separately from verification.
- Compute documented metrics on fixed data splits.
- Record experiment configuration and versions.
- Produce error analyses and reproducible outputs.
- Test abstention behavior and evidence provenance.

### 4.9 API boundary — future milestone

A REST API may later expose the pipeline through a framework such as FastAPI.

Expected concerns:
- Request and response schemas.
- Input validation.
- Controlled error responses.
- Request size limits and timeouts.
- Logging that avoids unnecessary sensitive input retention.
- Health checks and API tests.

The API is not considered implemented until its code and tests exist.

# FEVER Baseline Verification Experiments

## Objective

Establish reproducible claim-only classification baselines for the three FEVER labels:

- `SUPPORTS`
- `REFUTES`
- `NOT ENOUGH INFO`

These models provide a reference point for future evidence-grounded verification.

## Dataset

| Split | Examples |
| ----- | -------: |
| Train |  145,449 |
| Dev   |   19,998 |

The dev set contains 6,666 examples per class.

## Models

### 1. Majority-class baseline

Predicts the most frequent training label for every dev claim.

- Accuracy: 33.33%
- Macro-F1: 16.67%

### 2. TF-IDF + Logistic Regression

Configuration:

- Lowercase text
- Unigrams and bigrams
- Minimum document frequency: 2
- Maximum features: 200,000
- Sublinear term frequency
- Logistic Regression with `lbfgs`
- Maximum iterations: 300
- Random state: 42

Results:

| Label           | Precision | Recall |     F1 |
| --------------- | --------: | -----: | -----: |
| SUPPORTS        |    0.4407 | 0.8306 | 0.5758 |
| REFUTES         |    0.7635 | 0.4674 | 0.5799 |
| NOT ENOUGH INFO |    0.5442 | 0.2736 | 0.3641 |

- Accuracy: 52.39%
- Macro-F1: 50.66%

### 3. Class-balanced TF-IDF + Logistic Regression

Uses the same text features and classifier settings, with `class_weight="balanced"`.

| Label           | Precision | Recall |     F1 |
| --------------- | --------: | -----: | -----: |
| SUPPORTS        |    0.5156 | 0.5794 | 0.5456 |
| REFUTES         |    0.6560 | 0.6040 | 0.6289 |
| NOT ENOUGH INFO |    0.5001 | 0.4779 | 0.4888 |

- Accuracy: 55.38%
- Macro-F1: 55.44%

## Comparison

| Model                                       | Accuracy | Macro-F1 |
| ------------------------------------------- | -------: | -------: |
| Majority baseline                           |   33.33% |   16.67% |
| TF-IDF + Logistic Regression                |   52.39% |   50.66% |
| Class-balanced TF-IDF + Logistic Regression |   55.38% |   55.44% |

The class-balanced model is the current preferred claim-only baseline. It improves overall accuracy by 2.99 percentage points and macro-F1 by 4.78 percentage points over the unbalanced model. Its `NOT ENOUGH INFO` F1 improves from 0.3641 to 0.4888.

## Limitations

- Both trained classifiers use claim text only.
- Neither model retrieves or reasons over evidence.
- A predicted label does not establish factual truth.
- Results are measured on the FEVER dev split and are not final test-set results.
- The 90–95% accuracy target is aspirational and has not been achieved or validated.

## Reproducibility

From the repository root, run:

```powershell
.\.venv\Scripts\python.exe scripts\train_baseline_verifier.py
```

Machine-readable metrics are saved to `reports/retrieval/baseline_verifier_metrics.json`.

## Next step

Proceed to evidence-grounded claim verification, combining retrieved evidence with each claim. Evaluate retrieval and classification quality separately before measuring end-to-end verification performance.
